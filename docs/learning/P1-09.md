# P1-09：单Agent的Plan/Execute与ReAct闭环

本模块目标：让调查根据观察决定下一步，而不是永远执行同一串检索。必要前置是P1-07的可核验证据/固定流程和P1-08的授权/计划/状态。单Agent负责授权内的行动选择，不拥有批准新范围的能力。

按照当前约定，模块一次交付，练习直接给范例和参考答案。本模块工程实现、331项无数据库/98项真实PostgreSQL测试、获批的12次真实API请求及零新增请求回放已完成。结果未证明Agent优于固定流程，保留fixed默认。独立人工语义审查仍待进行；本次交付停在P1-09，等理解确认后再进入P1-10。

## 必要原理

ReAct闭环可理解为“观察 → 提出可核查的行动理由 → 选择工具 → 再观察”。例如首次只有召回摘要，没有继续监测条件，就应寻找调查结案材料并展开原文；引用到与初始假设冲突的车型或条件，应保留反证并调整假设，而不是写更长的回答掩盖缺口。

Plan/Execute在这里有两层：外层是用户批准的当前Control.PlanRevision；内层是调查中的假设、证据缺口和后续步骤。内层可以变，外层范围不能被模型自行扩大。内层记录是模型提议，不等于结论已经得到证据支持。

强基线不能只允许一次弱检索。本模块复用P1-07全部工具，并为两种方法建立相同上限的新比较配置；原P1-07一次生成默认和历史结果仍保留。资源上限相同不代表实际开销相同，必须报告多轮决策的输入、输出、耗时和审计开销。

## 关键代码与取舍

- `investigation/agent_contracts.py`：Decision白名单及参数约束；search只能带query，expand只能选择已有D候选，finish必须包含AnswerProposal，不能夹带任意批准字段。
- `investigation/agent.py`：确定性护栏后运行同步闭环，保存每轮planner修订、观察、支持与反对证据；原始资料和模型文本都不产生授权。
- `investigation/resources.py`：固定流程和Agent共用调用、输入、输出及时间额度；保守预留未知用量，不自动重试模型。
- `models/request_allowance.py`：本次本地实验的落盘请求预留账本，发送前扣额度，失败/在途请求计入批准上限，跨脚本重启不重置；不代替P1-11的服务级共享调度。
- `models/chat_api.py`：对无效内容JSON保存原文、finish_reason及usage诊断；用量未知保留null，不把失败当免费。
- `control/contracts.py`、`control/service.py`：Plan增加investigator选项；通过原执行凭证和发布事务运行Agent，保留撤销/暂停屏障。
- 对照脚本与共同配置分别为 `scripts/verify_single_agent_real.py` 和 `examples/single-agent-comparison.json`，评分仍调用P1-07现有工具。

上下文暂时完整保留，超额就停止，不偷偷截掉反证、范围或否定条件。高级摘要、分页和上下文选择继续在P1-10实现。后台worker和恢复仍在P1-11，本模块没有顺便实现多Agent。

## 从真实失败理解设计

决策协议与最终回答协议应明确分层。最初把固定回答SYSTEM和Decision说明拼在一起，出现了无效JSON/提前finish。当前每轮只要求一个Decision，最终AnswerProposal仅放在finish.proposal内；工具是否可用由服务器给出。普通调查初始没有D候选，先开放search；有候选后才开放expand。已有全集证据为零等确定性护栏仍可在调用模型前结束。

导航、原文和结构化结果承担不同职责。D001只是导航候选；E001等是当前运行的证据别名；来源编号用于识别资料，不能代替D别名传给expand。`source_fact`需要文字卡，`count`需要计数卡，`relationship`需要links产生的关系卡。JSON解析成功只证明语法，Decision校验负责行动，Claim校验负责引用类型和范围，独立语义审查再判断文字是否被证据支持。

真实Prius Agent选择一次检索和一次带关联展开，得到24张证据卡，却使下一轮输入超过24,000字符，因此保存证据、返回不足；没有发出第三次请求。真实车门Agent完成检索、两次展开和finish，但把文字卡用于relationship声明，最终回答被拒绝。这是待改进的策略和上下文问题，不能通过删除反证、放松验证或继续无界调用掩盖。

首轮在同一数据/模型/共同上限下比较；后两轮提示修复降低了剩余模型调用和输出额度，并回放原固定响应，属于开发修复，不能当成新的严格等预算实验。完整轮次、额外开销和限制见[对照记录](../experiments/P1-09-single-agent.md)。负结果仍是本模块交付产物；不据此删掉后续完整目标。

## 三个练习与参考答案

练习一：首次检索不足后改写查询。

范例：先查“braking safety”，只有笼统摘要；观察到缺少结案依据后，改查“ABS rough road investigation closed monitor”，再展开PDF中范围和Summary。

参考答案：第一次无命中或证据不够只是检索观察，不能写“没有召回”。新查询应解释要补哪个证据缺口，保留两次查询与候选轨迹，只有展开后的E证据才能支持最终结论。受控测试用人工注入首次空结果验证机制，不能把它当真实检索质量实验。

练习二：发现反例后调整假设。

范例：初始假设“同年款同部件的两次召回是同一缺陷”。17V331文本描述附件把手罩/侧碰，17V652描述拉索或进水结冰。两份原文是对“同一缺陷”推断的限制。

参考答案：将假设改为“存在相似症状，但缺陷同一性未确认”，记录原假设、反证别名、变更理由和未确认条件；最终不得丢掉已经记录的反证。它不是因果识别或个车适用证明。若模型给假设贴supported标签，评分仍要读原文，而不是信这个标签。

练习三：暂时超时后的有限重试。

范例：一次只读search抛TimeoutError，第二次成功。

参考答案：只读工具最多重试1次，两次attempt都消费工具额度。若第二次仍失败，观察必须记timeout和“不是成功零结果”，再决定用现有证据结束或停止。鉴权/引用完整性/Schema错误不重试；模型传输故障也不自动重试，因为无法确认前一次是否已计费。重试不能绕过授权检查。

额外边界：模型调用数、总字符或输出额度用尽时，返回证据不足并保存工具工件/证据卡/决策；不能继续第七次调用，也不把未验证假设当事实。总时长在步骤间检查，不宣称强制打断在途操作。

### 对照本轮失败的参考解法

范例：车门Agent已经展开两起召回，却想用两张text卡声明`kind="relationship"`。

参考答案：先调用允许的links取得结构化关系证据，再将关系结论限定在工具支持的类型和未确认条件；两份原文可分别形成source_fact，不能因症状相似就确认同一缺陷、因果或个车适用。若没有剩余调用额度，应保留两份来源事实和关系待核实项，避免提交缺证据的relationship。本次已保存失败不事后替换成该参考答案。

验证成功场景：下列数据库测试会运行真实工具链，检查search→expand、假设/反证保留和合法回答。验证失败场景：上下文超额应停止且不多调用模型；模型传输失败只调用一次；非法Decision或丢弃已记录反证应失败。测试资料与模型均受控，不代替实际模型质量实验。

```powershell

uv run --locked --offline python -m pytest -q tests/test_single_agent.py tests/test_request_allowance.py --basetemp .local/pytest-agent-exercises
```

无需改动真实请求账本来练习。`test_real_tool_loop_records_plans_evidence_and_verified_atomic_answer`验证合法闭环；`test_context_exhaustion_preserves_verified_evidence_without_an_extra_model_call`验证超额；`test_generation_transport_error_is_not_automatically_retried`验证传输失败不重试。完整本机数据库验证也会运行这些测试。
