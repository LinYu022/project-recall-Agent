## A：标准化先保证不丢信息

`entities/normalize.py` 复用原始记录版本，在另一个规则版本下生成实体投影。不会改写 P1-02 的内容哈希和数据。

```python
normalized = lexical(raw)
if normalized in allowed:
    return value | {"canonical": normalized, "status": "mapped"}
```

lexical 只处理 Unicode、空白和大小写，再查显式目录。近似名字仅生成 candidate，canonical 仍为 null。F150 可以提示 F-150，但查询必须使用精确已映射的名称；HS250H 不能自动并为 HS。项目目录仅覆盖当前探索样例，不是完整官方车型词典。

车型年严格区分整数、字符串、布尔、浮点与未知值；缺生产日期和配置时保留 unknown，不从车型年或叙述中补值。带证据的条件规范化与适用性判断将在下一小步继续实现。

数据样例提示部件分隔规则要看来源：投诉 `POWER TRAIN,SERVICE BRAKES` 是两个标签；召回 `SERVICE BRAKES, AIR:ANTILOCK:CONTROL UNIT/MODULE` 在当前源中是完整描述。采用同一个 split 函数会破坏召回部件身份。

规则详见 `docs/data/entity-mapping-rules-v0.1.md`。P1-02 原始字段、未知新增字段和旧版映射完整保留。

## B：投影单独存储并版本化

0003_entity_projections 新建三表：完整投影、车辆位置、部件位置。主身份为 source version_id + rules_version，另保存规则 JSON 的内容指纹。

`entities/store.py` 在一个事务中提交整批投影及子位置；重复投影无新增。沿用同规则名却改变内容会拒绝；使用新规则版本则可以并存。查询必须具有完全一致的规则指纹，不能混用新旧词典。

生产日期的 SQL 列当前为空，投影对象同时保存未知原因。数据库只是可查询派生层，不能反向篡改来源，未来规则变化也不会覆盖旧实验记录。

## C：EXISTS 过滤与不同 ODI 计数

一条投诉可能有多个产品和多个部件。直接连接会发生乘法：两个相同产品位置 × 两个部件位置 = 四行，投诉仍然只有一条。

`entities/counts.py` 使用参数化条件，并将车辆与部件的匹配各自写成 EXISTS。最后对来源记录键做不同值计数：

```python
vehicle_match = sa.exists(sa.select(1).where(*vehicle_conditions))
component_match = sa.exists(sa.select(1).where(*component_conditions))
```

这只判断有没有满足条件的位置，不把匹配位置复制成多条投诉。最终计数基于 `count(distinct(record_key))`；另返回 matching_component_rows 解释部件连接为何可能更多。

查询有固定的类型化入口，不接受 SQL 文本；执行在 PostgreSQL READ ONLY 和 REPEATABLE READ 事务中。先按明确 snapshot_ids 和时间模式选出版本；缺实体投影、规则漂移、模糊查询名会拒绝，历史不支持则返回 count=null。

当前结果只是所选归档响应中的标签计数，不是全国完整统计。没有从 top-k 检索结果计数，也没有把标签匹配解释为缺陷因果。
