# P1-14：情景记忆、历史任务搜索与浏览

本模块一次交付。目标是保存调查经历，让新任务能找到相关尝试、反证、失败和被否定的假设，并按需展开；历史只提示查什么，当前结论仍由当前证据支持。依赖P1-13的用户/项目空间与失效机制，复用P1-10/P1-11的工件、授权、日志和恢复。

## 必要原理

语义记忆偏向“已确认的偏好或约定”，情景记忆描述“某个任务在某个数据版本上发生过什么”。一份历史任务即使最终完成，也可能证据不足；一条被标记contradicted的假设仍是当时模型的提议状态。记忆不能把它自动变成普遍规则，也不能用相似叙述确认当前个车适用。

因此检索顺序是权限/项目 → 车型/年份及条件 → 来源/版本/时间 → 症状相关度。若先取相似top-k再排除错误年份，正确历史可能已被挤掉。失败任务同样可以提供有用线索，不能只保存COMPLETED或成功答案。

摘要负责导航，原报告与原始来源负责审计。默认摘要保存范围、版本、尝试、反证数量、失败标签和被否定假设，省略最终回答正文。需要细节时，先按事件锚点看邻近片段，再通过服务器登记的来源句柄回查历史原文。旧原文仍属于旧版本，不能直接成为当前E证据。

## 代码阅读与设计取舍

1. `memory/episode_projection.py`：确定性投影，保留否定/失败并排除answer和最终claim.statement；不调用摘要模型，不把模型标签当独立审查。
2. `memory/episodes.py`：捕获、去重、搜索、最近任务/任务内事件、锚点窗口与历史原文回查。检索前检查来源任务当前授权，索引/报告工件改变时明确失败。
3. `memory/episode_runtime.py`：从已批准计划构造只读检索边界，按任务提交时间截断历史，记录采用；生成前、步骤前后和发布前检查仍有效。
4. `investigation/agent.py`：history_search/window只提供导航观察，不创建证据卡，消耗原工具额度。回放工具结果后重新登记采用，保证恢复状态完整。
5. `control/service.py`及0008迁移：项目归档、三张持久表和可选索引失败记录。真实调查已完成而历史索引失败时保留调查结果，并标记history_capture_failed，不能把失败显示成空历史。

项目字段必须一致：project_id、memory.project_id和history.project_id不能分别指向不同空间。默认历史关闭；启用、换项目或允许跨版本要走现有精确计划审批。初选最多3条、每执行累计最多8条；固定、单Agent、并行工具及多Agent都可使用线索，但必须继续查询/校验当前数据。

检索目前采用可解释词项匹配，不宣称向量语义搜索收益。报告数组没有统一绝对时间，所以事件窗口沿明确标记的记录逻辑顺序浏览，不冒称并发调用的精确墙钟重放。初选准备开销单独记录，后续导航工具计普通额度。

## 两个练习与参考答案

### 1. 同车型、相似现象、不同年份

范例：历史A是2010 Toyota Prius，历史B是2011 Toyota Prius，二者描述相似刹车现象。当前任务限定2010年，查询只取top1。

参考答案：两者先检查当前调用者/项目，随后按年份过滤；B不得进入相关度排序，A才参与top1。若历史年份未知，也不能自动按2010年采用。生产日期/配置、来源、release和时间口径仍需继续检查。历史没有返回不等于现实中没有召回，也不等于没有别的历史任务。

成功验证：2011记录确实存在，2010查询仍返回A；扩大到另一项目或另一用户不能读到不属于当前空间的记录。失败验证：年份被删除或改变不能依靠文字相似继续采用；跨版本默认排除，明确允许后也只能作为线索，仍需当前证据。

对应检查：`test_same_symptom_different_year_or_project_never_occupies_top_k`、`test_future_tasks_are_excluded_from_adoption_snapshot_and_changed_release_is_explicit`。fixture年份和来源为合成；官方演示中的2011任务只是对固定2010资料作可用性检查，不伪造2011资料或真实召回结论。

### 2. 历史调查已否定的假设

范例：旧任务曾提出“相同刹车现象足以证明同一缺陷”，后来把H001标为contradicted，并保留反证。当前任务出现相同症状。

参考答案：检索摘要应显示这个否定状态及反证数量；按事件ID查看相邻尝试与结果，必要时回查旧来源和条件。它提示避免重复错误类比，但不能直接断言“当前一定不是同一缺陷”。当前任务仍须查询当前release的真实来源，保留未知；最终报告只能用当前E证据。

成功验证：否定标签和反证存在，history_window能定位，当前报告的证据全部绑定新任务；旧最终答案正文不进入模型历史上下文。失败验证：把历史的H/EP/HE或旧证据ID当当前E引用应拒绝；源任务撤销、历史停用或工件丢失时不能继续采用。若撤销发生在生成期间，在途响应可以留档，但正式发布必须阻断。

对应检查：投影、历史工具采用、源撤销、原文回查及恢复测试。contradicted在脚本演示里是受控模拟标签，不声称独立人工已证明一个真实缺陷推论。

## 本机API浏览范例

先按P1-13配置开发数据库/用户令牌并升级迁移，使用`python -m control`启动认证API、任务worker另行运行。以下浏览需要你自己的开发库已有授权任务；验收脚本使用临时schema并清理，不会把演示数据留进开发库。

```powershell
uv run --locked --offline python -m alembic upgrade head
$historyHeaders = @{ Authorization = "Bearer $env:RECALL_CONTROL_TOKEN" }
$historyApi = 'http://127.0.0.1:8001'
# 项目recall需已登记；Capture.task_id填写本机真实任务ID。
# POST /history/capture: {"task_id":"实际任务ID","project_id":"recall"}
$sample = Get-Content examples/history-query.json -Raw -Encoding utf8 | ConvertFrom-Json
$historyQuery = @{project_id=$sample.project_id; release_id=$sample.release_id; allowed_source_ids=$sample.allowed_source_ids; scope=$sample.scope; query=$sample.query; limit=5; allow_cross_release=$false}
$historyResult = Invoke-RestMethod -Method Post -Uri "$historyApi/history/search" -Headers $historyHeaders -ContentType 'application/json' -Body ($historyQuery | ConvertTo-Json -Depth 8)
# entries为空时先核对任务捕获、项目、版本、车型/年份、允许来源和授权；不要解释成现实无记录。
if ($historyResult.entries.Count -gt 0) {
  $episode = $historyResult.entries[0]
  $windowQuery = $historyQuery.Clone()
  $windowQuery.episode_id = $episode.episode_id
  $windowQuery.event_id = $episode.anchors[-1].event_id
  $windowQuery.radius = 2
  Invoke-RestMethod -Method Post -Uri "$historyApi/history/events/window" -Headers $historyHeaders -ContentType 'application/json' -Body ($windowQuery | ConvertTo-Json -Depth 8)
}
```

`/history/recent`使用相同筛选条件并支持next_before_episode_id游标；`/history/events/search`可附task_id搜索任务内事件。`/history/source`接episode_id、服务器返回的historical_source_handles.evidence_id和offset/page_size，回查结果明确标为历史来源。`/{episode_id}/state`用expected_revision启用/停用。

新任务采用历史时，计划明确加入`"history":{"project_id":"recall","enabled":true}`并审批。只需归档而不采用历史时可设置`"project_id":"recall"`。旧计划默认不启用，完成态任务不会被偷偷改写；所有者可显式捕获已有任务。
