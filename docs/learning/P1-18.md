# P1-18：公开仓库、复现与发行

本轮进入发行准备。实现、实际检查与剩余条件见[发行记录](../experiments/P1-18-release-preparation.md)。这份学习卡不把本地候选当作已发布的GitHub Release。

## 代码与关键取舍

`publication/export.py`只从暂存区读取，检查路径和已知敏感模式，生成另一个目录及逐文件映射。私人原文不分发，原始审计也不被匿名化脚本覆盖。公开派生物的哈希不能回填成原冻结哈希。

`scripts/verify_container_product.py`把构建、真实API调查、原文和重启持久化放在一个可重复检查入口，失败仍保存结果并停止自己的Compose项目。合成演示不产生真实模型质量分数。

MIT仅覆盖本项目原创代码和文档；第三方运行时、官方资料和模型分别保留许可边界。GitHub上传前检查的是拟公开副本及其全新历史，不能只检查当前工作区后把旧私人历史一并推送。

## 练习与参考答案

**一：公开副本的哈希为何不同？**

参考答案：个人路径、会话编号及私人审查被去除或隐藏，公开内容已经变化。需要同时保存原始摘要、公开摘要和转换说明，明确它是派生物。原确认结果仍是不通过，不能把匿名化后的摘要称为原冻结复现成功。

**二：公开目录检查通过，是否等于干净环境复现？**

参考答案：不一定。实际测试若复用既有解释器和已安装依赖，只验证了新源码目录不依赖原数据缓存。完全新依赖安装、容器启动和远端克隆还需分别实跑。镜像或依赖下载失败也属于未完成，不得因为原因是网络就填为通过。

**三：如何从结果追到实际证据？**

参考答案：公开引文失败见证保留C002、实际E003以及出现在别处而未被本句引用的E002。E003没有LFB触发条件，因此该原子不支持；“事实在另一证据存在”不等于当前引文已支持。一个反例足以否定零不支持目标，但不能据此填写尚未测齐的总体错误率。

**四：GitHub连接成功是否等于发布完成？**

参考答案：登录名、仓库权限、建仓能力、推送、tag、Release和远端克隆是不同的实际条件。必须核查远端分支/提交、tag指向、Release附件和运行入口。没有完成这些步骤时只能交付候选，不填写虚构仓库或成功状态。
