# P1-11：持久化调度、预算预留、取消与故障恢复

本模块把P1-08～P1-10的同步调查器放入持久化执行外层。学习目标是理解：消息可能重复、进程可能在任意时刻退出，但正式结果、执行权限和共享额度必须保持一致。一次模块统一交付，以下练习直接附范例和参考答案。

## 必要原理

“领取了工作”不代表永久拥有它。worker得到一个有期限的租约和新的执行代次；心跳可以续租，超过期限则旧worker失效。发布时还要核对任务版本，不能只检查一个running标记。新的worker可能重复读到同一个任务，因此提交和执行记录都需要幂等。

数据库无法与外部API共同完成一次原子事务。崩溃可能发生在预留后、发送后、收到响应后或保存后。我们可以保证同一执行代次只能发布一次，却不能保证外部provider永远只处理一次。缺少可验证响应时，宁可保留未知状态，不把“本机没有答案”当成“请求没有发生”。

预算也是共享状态。若父任务给每个子任务都复制4000输出额度，两个子任务就可能消耗8000。根任务池通过同一事务判断used+held+本次预留，只有拿到额度后才允许调用；失败、取消和重启不会让额度凭空重置。

## 实现与关键代码

- `control/queue_schema.py`与0006迁移：持久job、根任务预算池、逐步调用记录及执行租约字段，保留旧任务数据。
- `control/dispatch.py`：幂等入队、领取、心跳、截止、过期恢复、共享预留/结算及人工对账。恢复核对计划/授权、发布、模型、配置和工件。
- `control/journal.py`：相同已完成步骤重放；未知只读步骤可有界再试，未知模型请求不自动重发。输入变化则停止。
- `control/worker.py`：独立worker及故障注入点；P1-08仍决定授权和正式发布，P1-10上下文从已完成步骤重建。

执行epoch每次领取都变化。为了复用同一修订中已完成的模型决策，比较指纹只规范化上下文绑定里的epoch元数据；车型、年份、来源文字、授权、计划和所有其他参数都不放宽。实际输入保存当前epoch。新旧状态不能互相假扮。

旧同步开发入口保留给历史回归，但正式启动服务已接入Dispatcher，execute只入队。存在根预算池的任务不能通过旧execute或手动research绕过额度；可用已授权的报告/原文回查查看结果。这里的共享池覆盖一棵根任务树，不是账户月费钱包。

## 五个练习与参考答案

1. **worker退出。**范例：在模型响应已保存、下一步状态尚未推进时退出。参考答案：数据库仍记录running，租约过期后旧代次失效；新worker读取已完成的工具/模型工件，重建状态，不能为同一已完成请求再次调用provider。若退出在响应保存前，则不能认定已完成，未知模型请求保留额度并等待核查。
2. **重复投递。**范例：用户重复点击同一执行按钮，两个worker同时领取。参考答案：同一idempotency_key和同一请求返回相同job；换请求复用key报冲突。数据库中只有一个当前有效领取；没有租约的worker不能发布。发布成功但job标记未更新时，只补标记，不能再发布。
3. **主服务重启。**范例：重新构造服务连接并读取既有队列。参考答案：计划、授权、固定发布、调用工件和额度均来自持久记录；不从聊天记录猜测进度。模型/代码/配置或工件不一致时明确失败。恢复不等于重新批准，已撤销授权必须走现有批准流程。当前实验重建服务对象，未声称测量整机重启。
4. **旧worker在租约过期后恢复。**范例：worker A停顿，B重新领取，A随后返回结果。参考答案：B获得更大的epoch和独立凭证；A续租、发新调用和正式发布都应失败。已在途的返回可以私有保存和结算，但不能覆盖B的状态。不能假装远端调用已被强制取消。
5. **争用最后一份额度。**范例：同根任务两个子任务同时申请最后一次模型调用。参考答案：used、held和本次请求在同一事务判断，只有一个预留成功；失败方不发请求。拿到完整usage后只释放未用输出部分；未知usage保留全部预留。新建子任务、恢复和更换idempotency_key都不能获得第二份根额度。

成功判据不是“最后都变成COMPLETED”。取消应保持CANCELLED，未知响应应等待核查，不可恢复的任务应FAILED；COMPLETED只表示交付完成，语义质量仍须独立审查。

```powershell
# 不访问外部模型/资料；先确保父目录存在：

```

数据库练习使用合成来源与模拟模型，故障点通过InjectedCrash、受控阻塞和租约时间注入触发。验证成功恢复、并发预留与结算；也验证未知响应不重发、原文/工件缺失、旧授权、运行组件变化、截止、重试耗尽、取消后迟到结果及已发布后的崩溃。测试会保存失败状态，而非把失败算成成功。

真实进程实验使用已有官方Prius冻结包和明确的模拟abstention模型：第一个worker在保存响应后以23退出；恢复服务对象、注入租约过期与退避到期，再启动第二个独立进程。第二个重放1份模拟响应和4次工具输出，新增生成0，最终只发布一次insufficient_evidence。来源是真实官方资料，进程退出是真实退出；租约时间变化是故障注入，模型推理与token计数不是实际provider实验。

## 本机服务使用方式

先按现有数据库文档配置专用开发库并执行`uv run --locked python -m alembic upgrade head`，沿用P1-08的用户令牌和发布目录设置。两个进程使用相同数据库及`.local/control`工件目录：

```powershell
# 终端一：认证API。execute现在只入队。
uv run --locked --offline python -m control
# 终端二：持续领取与心跳；Ctrl+C后可重新启动。
uv run --locked --offline python -m control.worker
# 也可只领取一个job后退出：
uv run --locked --offline python -m control.worker --once
```

正式worker使用本机配置的模型，实际执行可能产生API费用；本模块验收脚本显式使用模拟模型，没有发送新请求。服务和worker的模型、context-mode和配置必须一致；需要旧上下文模式时两端都指定`--context-mode full_history`。不要用真实凭证启动故障实验的生成步骤来冒充免费回归。

认证接口：`POST /tasks/{id}/dispatch`传expected_version、idempotency_key及可选截止/重试/租约；`GET`同一路径看job、根池与调用状态。暂停/取消/撤销沿用原接口。旧授权失效后先恢复/批准当前任务，再用`POST /tasks/{id}/recover`检查旧job能否继续；计划或授权已换则旧job失败，需要明确提交新job。`/reconcile`接受call_id、completion_tokens、note，记录用户对账说明，不补造缺失响应；未知响应即使完成费用对账，也不会自动重新生成。
