# 带证据的范围事实与 EntityLink 规则 v0.1

日期：2026-10-26。适用：P1-03 的固定 JSON 快照教学，不是正式数据发布或个车召回查询。

## 事实层与关系层

`examples/scope-rules.json` 保存 scope-rules/0.1、嵌入的 entity-rules/0.2 及 7 条显式审查规则。0.2 仅扩充本步使用的精确车型/部件标签；上一小步的 entity-rules/0.1、数据库投影和计数口径保留。范围对象使用 0.2，不会把它与旧计数投影混用。

每条事实固定一个 source_version_id、字段、完整条件摘录、规范值及审查说明。`build_scope` 重新验证快照原字节，按 source-record/0.1 重建记录版本，再要求摘录在该字段中恰好出现一次。返回快照 ID、来源 URL、body/记录/字段哈希、行/字段指针与字符偏移 `[start,end)`。偏移作用于解码后的 JSON 字段字符串，不是原始 UTF-8 字节偏移。

这些规则由实现代理逐项对照原文编写，不是独立人工标注。字节/摘录校验只能证明出处，不能自动证明规范值的语义正确；新来源、新版本或未审查条件保持未知，审查仍是必要步骤。请求只能选择两个来源位置，不能提交一份自称“官方已确认”的事实对象。

投诉文本不是官方声明：即使能回放投诉中的召回编号，也拒绝把它作为 officially_referenced 的事实。条件事实当前要求唯一车辆位置；多产品记录仍可参与三元组/症状判断，但未明确绑定车辆位置的生产或配置条件会失败，避免整行条件被误用到每一辆车。按位置表达复杂条件属于后续规则扩充，当前不会猜测。

生产范围是来源所述的一批车辆的制造日期区间，采用包含两端的日期。它不会填进某辆车的 production_date；车型年也不能替代实际制造日期。14V284000 的区间规范为 2006-08-18 至 2010-09-11，单车日期仍未知。

配置采用显式键和值域；只有同一键下经过审查、互斥的值才能据不同值判断冲突。不得把自由叙述字符串的“不完全相等”当作互斥。20V332000、22V150000 的 engine 为 3.5L ECOBOOST。17V331000 摘录完整保留原车黑色/车身同色门把手与后续经销商镀铬配件条件，规范标记 POTENTIALLY_EQUIPPED 只保留来源的可能性，不能解释为某车已安装。

症状标签是审查后的描述性抽象，DOOR_UNLATCHING 不等于同一缺陷。官方引用保留原始提及编号，例如 20V-332；仅对明确审查的编号格式对应到 20V332000，不使用近似车型匹配来解析编号。

## 五类关系及晋升规则

| 类型 | 必需字段/证据组合 | 确认、否定和未知处理 | 允许表述 |
| --- | --- | --- | --- |
| scope_overlap | 双方品牌/车型/车型年位置证据；双方已有范围/配置事实 | 存在共同的精确车辆三元组且没有已知条件冲突时，确认**已记录维度的重叠**。已知车型、年份、制造区间或互斥配置冲突则 rejected；仅有近似候选则 candidate。缺失条件不视作满足 | “已记录的车型年范围重叠；个车适用性未确认” |
| symptom_similar | 双方各自的原文摘录与共同审查症状标签，必须联合出现 | 共同标签才能确认；仅部件相同、文本相近或缺审查标签均保持 candidate。范围排除不自动抹掉描述相似关系 | “两份描述具有相似症状；缺陷身份与因果未确认” |
| officially_referenced | 左方包含完整编号的显式提及摘录 + 右方正式编号和固定记录版本 | 有向确认：左提及右不推出右提及左。编号只是来自接口选择条件、猜测或不在摘录中，不得晋升。否定句里的提及仍只证明“提及”，不表示认可 | “左来源显式提及右编号”；如要断言扩展、支持或归因，须另做语义校验 |
| excluded_by_scope | 至少一项已知不相容的车辆三元组/制造范围/同键互斥配置，以及双方版本证据 | 已知冲突足以确认排除，即使其他条件未知。部件标签不同本身不作为车辆范围排除；无已知冲突只保留 candidate，不表示已适用 | “这两个已记录范围在某个已知条件上互斥”；不推出无缺陷 |
| applicability_unknown | 双方版本、已检查字段、所有未确认条件 | 无决定性排除且仍有日期/配置/个车成员等缺口时，确认“适用性未知”；已有决定性范围排除则此类型 rejected，保留缺口供审计 | “当前条件不足以确认完整适用性，需补列出的信息” |

`confirmation_status` 表示该**关系类型**的依据是否成立，只有 confirmed/candidate/rejected。`stage` 将确认的 excluded_by_scope 显示为 excluded、确认的 applicability_unknown 显示为 unknown，便于阅读。二者不是两个互相竞争的业务结论。

一个对象对可同时有 confirmed 的 scope_overlap、symptom_similar 和 applicability_unknown：已记录车型年相同、宽泛症状相似，但完整适用性未确认。candidate 不授权输出肯定句；其 allowed_wording=null。所有结果的 causation 都是 not_established。

每条关系绑定两端 scope_id、source_version_id、快照与原文位置，保留全部上下文 evidence 和该类型的 supporting_evidence。后者用于展示支持依据，前者不能全被视作支持当前关系。规则名称和指纹固定；未来调查还需做时间选择与发布完整性验证。

## 实际实现与保存

- `entities/scopes.py`：类型契约、固定版本事实和摘录回放。
- `entities/links.py`：确定性五类判断、关系内容指纹及不可覆盖工件。
- `entities/__main__.py`：scope/link 命令，不连接数据库。
- `evals/entity-link-reference-v0.1.json`：3 组原文对照及参考回答，明确不是独立人工金标准。

结果按内容哈希写入 `.local/entity-links/`；重复保存无变化，篡改、规则同名内容漂移会被拒绝。规则收据、结果文件不是跨文件原子事务；失败可能留下可重试的规则收据，不会切换正式发布。此步没有新建数据库表，不改动旧迁移；后续 API 继续使用这些固定工件，正式 DatasetRelease 在 P1-06 绑定。

底层 link/CLI 只检查给定 JSON 快照，不支持传入历史截止日期，也不声称这些版本在召回当年已被本地观察。dataset_release=null，time_mode=snapshot_only。第三小步已增加 `entities/query.py` 与查询 API，在底层评估前执行 P1-02 时间筛选，并用外层查询对象固定时间断言；正式发布仍待 P1-06 验证。PDF/通用文档解析仍属于 P1-04。

审查目录有意有限：不是通用自然语言条件抽取器、全部车型配置词典、VIN 成员判定器或缺陷因果模型。当前支持样例的生产区间和配置已规范化，其他内容继续保留未知，不将功能缺口伪装为数据已确认。
