# P1-07：固定调查流程与证据校验

版本：fixed-investigation/0.1。完整后续目标仍按原计划，本文没有实现 P1-08 授权生命周期或 P1-09 自主工具规划。

## 在架构中的位置

P1-00 提供任务边界和评分问题；P1-03 提供实体范围、去重计数和关系检查；P1-04/05 提供可回放原文和检索；P1-06 固定完整发布及允许来源。本模块把这些能力串成确定的工具顺序，输出原子 Claim、Evidence 和运行工件，作为后续单 Agent 的强基线。

```mermaid
flowchart LR
  R[任务与固定发布] --> G[时间与必要条件检查]
  G --> L[允许资料全集结构化查询]
  L --> C[按题型计数或检查关系]
  C --> S[固定检索与多来源展开]
  S --> E[证据卡及出处回放]
  E --> M[一次 JSON 模型提议]
  M --> V[结构 引用 上下文 范围校验]
  V --> A[原子结论渲染与运行留档]
  A --> H[独立语义审查与评分]
```

## 固定访问顺序和预算

1. `FrozenContext` 通过 `Catalog.task()` 验证活跃任务、发布哈希、文件和数据库一致性。加载该发布已经冻结的时间选择及允许来源。
2. 对比显式请求时间；与发布不同则 `unsupported_time`。检查声明的必要条件；个车适用问题至少要求品牌、车型、年款、生产日期和配置，不全则 `needs_clarification`。这些检查不调用模型。
3. 枚举所有允许、可见的召回记录版本，按相同范围规则分为 matched/pending/excluded。缺记录元数据保留 pending；没有召回来源则 unsupported。只有 complete 且匹配数为零，才支持限定于这些资料的 `no_matching_records`。
4. 统计题调用 PostgreSQL 去重计数，不把检索条数当计数。缺投诉来源或不支持的筛选返回证据不足。统计题仅把聚合结果送入外部模型，不发送完整投诉叙述。
5. 若请求指定关系端点，调用既有时间及来源受限的关联检查。端点允许在题目范围外作排除检查，结果标记 inspection，不能当作适用确认。
6. 其他题固定 hybrid 检索，默认每通道 top 6，按来源多样性优先选择最多两个展开。跟随明确的官方引用，保留已实现的父段和范围上下文；不由模型自由决定新工具。
7. 工具上限 6，生成上限 1；失败不自动重试。完整上下文超出 24000 字符时失败留档，不悄悄截掉条件；生成上限 2000 tokens。程序的证据重放另记 `origin_replays`，不是可供模型调用的工具额度。总耗时包含检查开销。

这里固定来源多样性优先的策略不保证挑到答案；工具等价性指允许的数据访问能力，后续比较还须冻结相同请求、主模型、来源、限制和评分版本，并如实报告工具实际开销。

## 证据卡与结论

`evidence_id` 对卡体内容取哈希；`evidence_key` 表示稳定证据内容，便于不同运行对照。两者不能互换。卡体含 task/release、来源版本、工具输出工件哈希及定位路径、原文引用或结构化结果、范围通道、必要上下文卡 ID。先统一成JSON可持久化表示，避免工具内存中的元组落盘成数组后产生误报。

模型以 E001 等本次运行别名引用卡，同时能看到可读来源ID、原文和版本定位。别名不是跨运行标识；真实 ID 保存在报告里。文字卡由服务器从展开结果建立，焦点卡要求完整直接父段和显式范围上下文，上下文卡本身的范围依赖也递归保留并检查环/缺失。结构化卡保存完整工具输出。模型不构造证据、修改发布或执行工具。

`verify_cards()` 不只比对哈希：它读取输出工件，核对定位路径；对文字重放发布中的原始字节、解析和分块，再比对全部节点、引用、来源、范围及依赖；对结构化结果重新执行确定查询。即使攻击者同时重算卡片和输出工件哈希，伪造事实仍会被原始资料重放拒绝。

`verify_proposal()` 检查结构、别名、固定范围、必要上下文、证据种类及通道。生成后先确定性补齐模型已经看到的必要上下文卡，保留原始输出并记录每条Claim新增的上下文别名；不新增外部证据、不改写结论。补齐后再严格校验，必要卡缺失、未知别名或错误范围仍拒绝。首轮开发结果保留了原始严格策略对上下文遗漏的拒绝，第二轮明确登记这一归一化策略。

未实现个车确认和因果识别工具，所以这两类确认声明直接拒绝。若模型把过强语句谎标为 source_fact，程序不能因此识别所有语义错误，仍需审查。`source_fact` 的支持引用需匹配范围文字；inspection关系卡可用于relationship、scope_exclusion和insufficiency。统计范围局限采用insufficiency，避免把样本覆盖局限误当实体范围排除。

没有独立自由回答字段；答复由已通过机械约束的原子 statements 和引用渲染。`execution_status=completed` 仅表示流程完成。`quality_status=pending_semantic_review` 不表示结论正确，也不把任务改为 P1-08 的 COMPLETED。

## 模型、凭证与复现

用户明确选择 `https://api.deepseek.com` / `deepseek-flash`。stdlib 适配器用 Chat Completions、非思考模式、temperature=0 和 json_object；返回后必须经过 Pydantic。JSON 模式不提供严格 Schema 或语义正确保证。finish_reason 非 stop、空/非法内容、HTTP/传输失败均拒绝，不重试、不打印响应体或密钥。

`.env` 只对白名单五个模型配置键作字面值读取，环境变量优先。数据库等其他配置仍由环境变量提供。`.env` 已忽略；日志、报告、提示词和 Git 不包含密钥。模型输入对 VIN、邮箱和长电话样式作最小替换；这是最小化处理，不宣称通用匿名化。

运行固定模型 ID、接口、提示词、参数、配置、输入/输出、provider 返回 model/id、真实 usage 和耗时。服务端权重修订不可得时记 null；温度零仍不保证云端逐字复现。计费价格未核验时费用为 null，不估造金额。`RecordedModel` 可按完整输入指纹回放实际 API 响应，模式明确记为 recorded_api_replay，不作为新模型实验。

DatasetRelease 的原始封包保持不变；主生成模型在调查运行清单中固定。P1-06 包内旧 pyproject 是当时发布环境，P1-07 代码及当前锁文件由 Git 固定，两层都保留。

## 存储和入口

`investigation` CLI 提供 run/blind/score/import-review。调查工件在 `.local/investigations/INV-.../artifacts`，开发验证在 `.local/P1-07/`。成功与失败运行均向发布目录登记报告保留引用。没有新增数据库迁移；Claim/Evidence 用内容寻址工件持久化，完整持久化任务恢复仍属 P1-11。工件文件与 PostgreSQL 没有共同事务，写工件后登记引用失败可能留下可调查的未登记文件，不能宣称已具备自动恢复。

已有查询应用保持原入口；仅显式注入 `investigator` 时增加 POST `/published/investigate`。默认查询服务不会自动取得外部生成能力。请求无法覆盖来源、范围、模型或预算。本机开发服务尚无身份鉴别及跨用户隔离。

## 评分边界

参考标签与模型输入分离。EvidenceSlot 允许等价 locator，完整父段覆盖窄引用时按来源版本、范围和子串哈希匹配；一个 ReferenceClaim 的 evidence_sets 外层 OR、内层 AND。结构化槽按预先冻结字段匹配。

程序输出执行状态、引用检查及槽覆盖；这些数字不冒充语义正确率。语义审查另外给 supported/partial/overstated/not_evaluable、对应参考结论、范围、反证、完整性和理由，并绑定精确报告/参考内容哈希。只有完整、无待决争议的 human 署名审查才填 formal_semantic_metrics；实现代理或合成审查只进 provisional 字段，缺审或不可评时为 null。当前尚未实现核验审查者身份的权限服务，reviewer_kind 是明确署名的记录，不能据其字符串自动宣称独立性。

盲审公开 JSON/HTML 隐藏方法、模型、运行 ID、路径和分数；私有映射留在忽略目录。独立人员尚未参与时，争议台账只能登记待审，不能编造裁定。新增有效证据按评分协议先盲审并版本化，再对所有比较方法统一重评分。
